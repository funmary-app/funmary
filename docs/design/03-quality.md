# 3. 品質

Funmary は、速さ、軽さ、サーバー負荷の小ささ、使いやすさ、壊れにくさを重視します。この章では、それぞれをどう守っているかをまとめます。

## 3.1 目標値

数字で決めておかないと、速さや軽さは少しずつ崩れます。次の値を目標にし、超えたら原因を調べます。

| 項目                                     | 目標                             | 測り方                                            |
| ---------------------------------------- | -------------------------------- | ------------------------------------------------- |
| 初回表示 (スマホ、4G 回線)               | LCP 1.5 秒以内                   | Lighthouse (リリース前に手動)                     |
| ページごとの JavaScript                  | 圧縮後 60 KB 以内                | CI でビルド結果の容量を検査し、超えたら失敗にする |
| 画面と API の応答 (サーバー内の処理時間) | 95% が 100 ms 以内               | 応答時間をログに出し、管理画面で集計する          |
| ICS とフィードの応答                     | 50 ms 以内。変更がなければ `304` | 同上                                              |
| メモリ使用量                             | 150 MB 以内                      | `systemctl status funmary` と管理画面             |
| 平常時の CPU 使用率                      | ほぼ 0% (定期処理の数秒を除く)   | `top`                                             |

ページごとの JavaScript の上限だけは、ビルドのたびに検査して守っています。ほかは、目標値として決めているもので、必要に応じて測って見直します。

## 3.2 速さと軽さ

### 端末に送るものを減らす

- 画面はサーバーで描画して返します (SSR)。初回表示のためにブラウザからデータを取りに行くことはしません
- 文字は、端末によらず同じ見た目にするため、LINE Seed JP を Funmary から配ります。日本語フォントは 1 ファイルにすると数 MB になるので、文字の範囲ごとに分けたファイル (Fontsource の形) を使い、ブラウザには画面にある字の分だけを読ませます。太さは本文と太字の 2 つだけにし、読み込むまでは OS の標準フォントで出します (`font-display: swap`)。外のサービス (Google Fonts など) からは読みません
- UI 部品は使うものだけを取り込みます。アイコンも、使ったものだけがビルドに入ります
- ビルド時に静的ファイルを gzip と Brotli で圧縮しておきます (adapter-node の `precompress`)。実行時に圧縮する CPU が要りません

### 2 回目以降をさらに速くする

- ファイル名にハッシュが付く静的ファイル (`/_app/immutable/`) は、1 年間キャッシュさせます
- リンクにカーソルを載せた時点 (スマホでは触れた時点) で、次のページのデータを先読みします (`data-sveltekit-preload-data="hover"`)

### サーバー内の処理を短くする

- SQLite は WAL モードで使い、よく使う検索には索引を張ります。better-sqlite3 の同期 API で、準備済みの SQL を使い回します
- 1 画面の表示で DB を何度も問い合わせないよう、必要なデータはまとめて取ります

## 3.3 サーバー負荷

- **外部からの取得を減らす**: 学生ポータルの HTML は、前回と同じハッシュなら解析と比較を省きます。公開シラバスは、科目の一覧を週に 1 回だけ取ります。詳細は、30 日以上前に取った科目と未取得の科目だけ取り直します。新年度の公開を待つ 3 月から 4 月の初めだけは、一覧を毎日確かめます
- **取りに来る側の負担を減らす**: ICS には `ETag` と `Cache-Control: max-age=900` を付けます。変更がなければ `304` を返し、本文を作りません
- **回数を制限する**: ICS、フィード、公開 API には、hono-rate-limiter で回数制限をかけます
- **通知はまとめて処理する**: 送信待ちの通知は 1 分ごとにまとめて取り出し、同じ送り先への送信は間隔を空けます
- **定期処理をずらす**: 取得の時刻に数分のゆらぎを入れ、ほかの処理と重ならないようにします

## 3.4 使いやすさ

- **スマホを基準に作り、PC でも使いやすくする**: スマホでは画面下部のタブ (ホーム、時間割、科目、設定)、PC では左側のメニューにします。アプリストア向けのアプリは作らず、Web アプリ (PWA) だけにします
- **今日の画面で用が済む**: 次の授業の時刻、教室、開始までの時間を一番大きく出します。休講や教室変更がある授業は、色と文言で目立たせます
- **データの鮮度を見せる**: 取得が 12 時間以上止まっていれば、情報が古い可能性を画面に出します ([3.5](#35-壊れにくさとフォールバック))
- **コピーと QR を用意する**: カレンダーの URL などには、コピーのボタンと QR コードを付けます
- **見やすさ**: ダークモードを選べます。文字と背景のコントラストは WCAG AA 以上にし、キーボードと読み上げでも操作できるようにします。時刻は 24 時間表記、日付には曜日を付けます
- **困ったときの出口**: エラー画面や空の画面には、次に何をすればよいかを書きます (例: 履修科目が 0 件なら登録画面へのボタン)

## 3.5 壊れにくさとフォールバック

### 原則

1. **取得と表示を分ける。** 外部のサービス (学生ポータル、公開シラバスなど) に接続するのは定期処理だけにします。画面、ICS、フィードは、DB に保存済みのデータだけで作ります。外部が止まっても、画面は前回までのデータで動き続けます
2. **前回の正しいデータを捨てない。** 取得に失敗したとき、結果が怪しいとき (件数の急減など) は、DB を更新しません
3. **失敗は 1 つのタスクの中に閉じ込める。** タスクごとに例外を捕まえ、1 つの失敗がほかのタスクや画面に波及しないようにします
4. **処理は何度やり直しても同じ結果になるように作る。** 途中で止まっても、次の周期でやり直せばよいようにします
5. **状態を隠さない。** 取得の失敗や情報の古さは、管理者には管理用の通知で、利用者には画面の表示で知らせます

### 取得元ごとの見張り

取得元 (学生ポータル、公開シラバス、学年暦、祝日) ごとに、連続の失敗回数を記録します。3 回続けて失敗したら、その取得元を「不調」とし、次の試行までの間隔を倍々に広げます (上限 6 時間)。不調になったときに、管理用の通知で 1 回だけ知らせ、画面には情報が古い可能性を表示します。成功したら、元の間隔に戻します。

### 起きうる障害と備え

| 起きること                                     | 影響                          | 備え                                                                                            |
| ---------------------------------------------- | ----------------------------- | ----------------------------------------------------------------------------------------------- |
| 学生ポータルに接続できない、ログインに失敗する | 休講が更新されない            | 前回のデータを表示し続ける。以後は上の見張りに従う                                              |
| 学生ポータルの HTML の構造が変わる             | 解析できない、件数が 0 になる | 件数の急減を検知したら DB を更新しない                                                          |
| 新年度の公開シラバスがまだ公開されていない     | 科目が見つからない            | 前年度の科目を使い続け、毎日確かめる                                                            |
| 学年暦を取得できない                           | 学期の期間が分からない        | 手入力、推定の順に切り替える                                                                    |
| 祝日の CSV を取得できない                      | 祝日が更新されない            | 前回取り込んだ値を使う。1 度も取れていなければ同梱の CSV を使う                                 |
| Discord や Webhook への送信に失敗する          | 通知が届かない                | 再送する。直らなければ、その送り先を止めて通知欄で知らせる。通知欄とフィードには必ず残る        |
| 外部の応答が遅い                               | 定期処理が詰まる              | 通信のタイムアウトは 15 秒。タスク全体にも締め切りを設け、同じタスクは同時に 1 つしか動かさない |
| プロセスが落ちる                               | 数秒間止まる                  | systemd が 5 秒後に再起動する。定期処理と送信待ちの通知は続きから再開する                       |
| メモリが漏れる                                 | 動作が重くなる                | systemd の `MemoryMax` を超えたら再起動する                                                     |
| DB が壊れる                                    | 起動できない                  | 起動時に `PRAGMA quick_check` で確かめる。問題があれば起動を止める                              |
| マイグレーションに失敗する                     | 新しい版が起動しない          | 実行前にバックアップを取る。失敗したら起動を止め、更新スクリプトが前の版に戻す                  |
| 設定が足りない、間違っている                   | 起動できない                  | 起動時に環境変数を Valibot で検証し、何が足りないかを書いて停止する                             |
| VPS が止まる                                   | すべて止まる                  | カレンダーアプリは前回の予定を表示し続ける。外部の監視で気づく                                  |
| 緊急で取得を止めたい                           |                               | `SOURCES_DISABLED=portal,syllabus` のように、取得元ごとに止められる                             |

### 止めるときは静かに止める

`SIGTERM` を受けたら新しい処理を受け付けず、実行中の処理が終わるのを待ってから DB を閉じます (adapter-node の終了の仕組みを使い、待つ時間の上限は `SHUTDOWN_TIMEOUT` で決まります)。systemd の再起動や更新で、書きかけのデータを残さないためです。

### 壊れにくさを確かめるテスト

- パーサーは、保存した正常な HTML に加えて、列が欠けた HTML、空の表、ログイン画面に戻された HTML でも試します
- 外部への通信を差し替えて、タイムアウト、500 番台、429 のときの動きを試します
- 日付を差し替えて、年度の境目、学期の境目、祝日と振替授業日が重なる日を試します
- Playwright で、ログインから時間割の表示、通知欄までの主な流れを毎回の CI で通します。スマホの幅と PC の幅の両方で試します

## 3.6 ログ

障害の調べやすさはログで決まります。ログは consola で出し、1 か所 (`@funmary/log`) にまとめています。

- 取得元やタスクごとにタグを付けます (`[portal] 取得に成功 (12 件、前回から変化なし、820 ms)` のように、何が起きて、どれだけかかったかを 1 行で読めるようにします)
- 出し方は環境で切り替えます

| 環境              | 出し方                                                                                                                                                      |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 手元の開発 (端末) | consola の標準の表示。レベルごとの色とアイコンが付く                                                                                                        |
| 本番 (systemd)    | 1 行 1 件の素の文字列にし、色は付けない。行の先頭に `<3>` のような優先度を付け、journald にレベルを伝える。`journalctl -p warning` で警告以上だけを見られる |
| `LOG_FORMAT=json` | 1 行 1 件の JSON。あとで集計したいとき                                                                                                                      |

- レベルは `LOG_LEVEL` で変えます
- HTTP の応答は、Hono のミドルウェアと SvelteKit のフックで、メソッド、パス、状態、処理時間の 1 行にします
- トークン、Webhook の URL、メールアドレスは、出力する前に伏せます。`/cal/<トークン>.ics` は `/cal/***.ics` と出します。伏せる処理はロガーの中の 1 か所にまとめ、書き忘れが起きないようにします
